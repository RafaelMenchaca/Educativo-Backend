## Autoridad y clasificacion inicial (historico 2026-10-31)

Las incertidumbres y cantidades de esta seccion describen la auditoria previa. La evidencia y decision vigente del 2026-11-02 figuran al final; la matriz declarativa contiene ambas clasificaciones.

PUBLIC en una policy incluye todos los roles; no equivale al rol PostgREST anon. Grant y RLS son puertas independientes. Tras B0, anon no tiene grants public, pero ello no convierte una policy en candidata C1 ni demuestra que su rol sea correcto. Un rechazo 42501 post-B0 prueba la puerta de grants; no aisla el efecto del rol RLS.

El codigo configura admin sin Bearer de usuario; eso demuestra intencion administrativa, no el atributo catalogal efectivo de una clave. Los documentos revisados no registran un valor observado de `rolbypassrls` para service_role. El diagnostico historico contiene una consulta de atributos, no su resultado versionado. **No se supone bypass generico.** El preflight devuelve rolsuper/rolbypassrls/rolinherit, owners y memberships transitivas de los tres roles; la falta de un rol o cualquier membership bloquea contexto. `service_role_bypass_observed` es un resultado futuro, no una afirmacion de esta auditoria.

Postgres es owner versionado de las tablas y estas tienen NO FORCE; ese contexto explica la exclusion del owner del filtro RLS ordinario sin asumir que postgres sea superusuario. handle_new_user es SECURITY DEFINER owner postgres, invocado AFTER INSERT auth.users; inserta exclusivamente profiles/settings. C1 fijo search_path a pg_catalog,public y retiro EXECUTE runtime. La provision no requiere TO PUBLIC para el rol de Auth bajo ese contexto; aun asi el contrato de cuentas permanece B4.

Las otras cinco funciones son invoker: set_updated_at solo modifica NEW; enforce_grado_ownership lee planteles, enforce_materia_ownership lee grados, enforce_tema_ownership lee unidades y enforce_planeacion_tema_ownership lee temas (acepta null). Se ejecutan bajo la autoridad del escritor; no cambian magicamente a postgres por pertenecerle. Lecturas con authenticated conservarian policies authenticated; llamadas desde admin requieren resolver su autoridad. Hay 16 triggers versionados: 15 public y uno auth.users; 11 usan set_updated_at. Las FK y cascadas no se reinterpretan como nuevos consumidores anon.

Clasificacion excluyente por policy:

- NARROW_CANDIDATE: dos INSERT de examen, con consumidor authenticated demostrado. El worker lee/actualiza esos objetos, pero no inserta jobs/items; cambiar solo el rol de INSERT no gobierna esas otras operaciones. Sin triggers de aplicacion sobre jobs/items. Owner postgres/NO FORCE permanece; service_role INSERT no tiene consumidor demostrado. Grants I se conservan; relecturas S y cleanup D permanecen separados. No se necesita ampliar autoridad administrativa.
- KEEP_PUBLIC: cero; no hay contrato demostrado que necesite otro rol sujeto a RLS. La incertidumbre sobre bypass no se disfraza de KEEP_PUBLIC.
- ALREADY_AUTHENTICATED: una SELECT de ai_model_prices; el rol ya tiene el limite solicitado. Esto no aprueba conservar indefinidamente su grant/contrato de visibilidad: B4 decide esa superficie.
- DECISION_REQUIRED: 24. Consumidores admin/fallback o lecturas invoker comparten la operacion; no hay evidencia suficiente de su autoridad efectiva. SELECT items ademas carece de consumidor productivo authenticated demostrado. Antes de reclasificar se requiere evidencia catalogal y, donde corresponda, regresion de consumidores; no una nueva autoridad.
- LEGACY_OR_DEFERRED: 22. Catorce policies de metricas/perfiles/user_profiles pasan a B4/03D3C3; siete policies especificas mas ALL temas cubren las ocho dependencias diferidas a 03F. ALL temas incluye S/I/D productivo y U test-only: no se divide ni altera para facilitar B3.

Las dos candidatas son **consideraciones offline**, no allowlist ejecutable. Todas las filas mantienen `future_allowlist=false`. Su reversal conceptual consiste en restaurar exclusivamente la lista de roles PUBLIC conservando nombre, comando, modo y expresiones; no hay archivo ni sentencia de rollback. Regresion existente: 03D2C-PREP-EJOB-A/B, 03D2C-PREP-ITEM-A/B y CREATE-OWNER-A, con relectura y cleanup. Brechas: repetirlos despues de un cambio autorizado, comprobar metadata exacta de roles y conservar prepare/compensacion/polling sin generacion real. Ninguna prueba de esta sesion modifica RLS para simular el cambio.

Las cinco policies de planeaciones permanecen separadas. ALL es permisiva y se solapa con cuatro especificas; estrechar solo una no reduce el conjunto habilitado por las demas. `update own planeaciones` no tiene WITH CHECK explicito: se conserva NULL, sin convertir la regla efectiva de reutilizar USING en una expresion inventada. No se consolidan policies.

## Preflight de auditoria original y validacion historica

[SQL B3](test-environment/03d3c2_b3_policy_preflight.sql) contiene una unica sentencia WITH RECURSIVE/SELECT sobre catalogos, sin filas de aplicacion, SQL dinamico, DO, DDL ni DML. Devuelve un objeto con sesion/version, todas las policies public y RLS/FORCE, ACL directas (incluyendo PUBLIC y grantor), 456 celdas de grants efectivos, memberships directas/transitivas con caminos acotados contra ciclos, atributos de roles, owners, ACL de secuencia y resumen fail-closed. PG17 de test es el contexto esperado; no prepara promocion a produccion ni acredita Project ID mediante SQL.

Resumen: manifiesto exacto de 19 tablas; comparacion completa de 49 policies mediante EXCEPT en ambas direcciones; 48 PUBLIC y una authenticated exclusivamente en precios; RLS 19/19, FORCE 0/19; grants post-B0 exactos por identidad y privilegio, sin grant options ni grantors adicionales; secuencia post-B2 con USAGE authenticated/service_role, postgres S/U/USAGE y anon/PUBLIC vacios. Roles ausentes, columnas NULL inesperadas, memberships o drift bloquean `catalog_context_matches`. `apt_to_apply` permanece literal false incluso si todo coincide. La ejecucion read-only futura no esta realizada ni se confunde con aptitud para cambios.

El fingerprint completo MD5 incluye schema, tabla, nombre, comando, modo permisivo/restrictivo, roles ordenados, USING y WITH CHECK; se deriva del inicializador con orden C y separadores deterministas. MD5 se usa para detectar drift, no como firma de seguridad; la igualdad exacta bidireccional es independiente del hash. No se reutiliza el hash parcial de B1/B2, que omitia expresiones/permissiveness. Una diferencia representacional del deparser tambien detiene la comparacion y exige diagnostico; no se normaliza agresivamente para esconder cambios.
